# Web probes

Checks worth running on most web apps, after the adapter's own journeys, in this order (each leaves state the next one uses). For a broader UX checklist, `agent-browser skills get dogfood` has an issue taxonomy.

- **Auth and the active context.** Sign up a new fixture account (number, code from the dev inbox, profile, company), log out, sign in again, switch company, log out again. A number with an account and one without must get the same code step: deliberate anti-enumeration, never a finding.
- **Signed-out redirects.** Open a protected page with no session: note the status and the landing URL (the adapter's pattern, e.g. `/auth?next=/app/products`), then sign in and check you return to the page asked for. A redirect that replays a form post at the sign-in page (a 307 or 308 where a 302 or 303 belongs) is a bug; one that lands somewhere unexpected may be the documented redirect working, so check the adapter first.
- **Two tabs, two contexts.** Where a user can switch account, workspace or company, open a second tab, switch it, then save in the first: the save must land where the first tab says it is, and no tab may show the old context's data after a switch. This is the highest-value finding on the auth journey.
- **Roles.** Repeat a privileged page and its actions as a lower role, and as a non-staff member of a staff-only area: the page and its data must refuse, not just hide the button. Staff areas: create a root item, a child, then add a field to the root and the same key to the child; a key already taken along one line (ancestors, descendants, retired keys all count) must be refused, a retired field must not be editable or re-addable under its old key (append-only trees), and a reload must not leave an old tree on screen.
- **Forms.** Submit empty, too long, mixed scripts and digits (Latin, Persian, Arabic where the product serves them), and pasted whitespace. Each error sits next to its field and says what to do; the typed values survive the error. Watch for fields the product deliberately does not have (a price on an item whose price lives elsewhere), client-side re-sorting of a page the server ordered under a locale collation, and validation text from a hand-written schema instead of the generated one, when the adapter names such rules.
- **Lists.** Create an item, list it, reload, check persistence. Empty state on a fresh account; page to the end; add a row while paging and check nothing repeats or vanishes (keyset paging); filters and search survive a reload when the product says they should.
- **Audit log.** As an admin, after the other journeys, open the audit view and page to the end. An action id that renders raw (`area.thing.added`) because the web has no label for it means the view must still render and the label is missing; a page that loses or repeats a row while paging is the keyset bug; a timestamp in the wrong calendar or numerals for the locale, or formatted at the component instead of through the project's formatter, is a finding. Entries with no actor on purpose (an e-signature provider's callback) are not (adapter).
- **Persistence.** After every save, reload and open the item fresh.
- **Locale and direction.** Switch language on the sign-in page and inside the app: the address behaves as the product says (a locale segment appearing in any URL, or `/en` answering as a page, violates a no-locale-in-URL rule when the adapter says so), the choice (usually a cookie) survives a reload, a new tab and signing out and in, and a soft switch keeps a half-filled form's values. Under right-to-left, icons and margins mirror (a margin that did not mirror used a physical property instead of a logical one); dates, digits and numbers follow the locale; no untranslated string.
- **Narrow screen.** Re-run the main journeys (auth, and the staff or admin area) at 375 px wide (`agent-browser set viewport 375 812`): no sideways page scroll on the body, every control reachable (none under the fold with no way to scroll to it), tables scroll or stack.
- **Screen vs response.** For anything numeric or listed, compare what the screen shows with what the network returned. Wrong on screen and right in the response is a rendering bug; wrong in the response is an API bug (`api-probes.md`).
- **Every failure, before you record it.** Capture the console errors and the failed or hanging requests at the moment of failure, then reload and reproduce from a fresh load. A hot-reload overlay, a dev-only warning, a timing artifact or a container still starting is not a product bug.
